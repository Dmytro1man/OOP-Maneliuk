## Опис реалізації

У цій лабораторній роботі реалізовано власні типи винятків та патерн `Result` для більш контрольованої обробки помилок[cite: 20]. Згідно з варіантом 15, створено клас `MessageProcessor`, який імітує обробку повідомлень[cite: 22]. Метод `ProcessMessage` викидає власний виняток `MessageProcessingException`, якщо повідомлення пошкоджене, а метод `SendMessage` повертає об'єкт `Result<bool>`, інкапсулюючи помилку без використання винятків, якщо одержувач невалідний[cite: 20, 22]. 

**Доцільність вибору між винятком і Result<T>:** 
Виняток `MessageProcessingException` доцільно використовувати для непередбачуваних та критичних ситуацій (наприклад, коли структура даних фатально пошкоджена і подальша обробка неможлива). Натомість патерн `Result<T>` ідеально підходить для "нормальних" або очікуваних сценаріїв невдачі, таких як невалідно введені дані (наприклад, відсутність '@' у відправленні), що дозволяє уникнути витрат ресурсів системи на генерацію стеку викликів[cite: 20].


## Відповіді на контрольні запитання

**1. Навіщо створювати власні типи винятків? Які переваги це дає?**
Власні винятки дозволяють створювати специфічні типи помилок, які чітко описують проблему саме у контексті вашого застосунку[cite: 20]. Перевагою є те, що їх можна вибірково перехоплювати в блоках `catch`, а також додавати до них власні властивості (наприклад, `MessageId` чи `Details`[cite: 22]) для передачі додаткової інформації про помилку.

**2. Які стандартні конструктори рекомендується реалізовувати для власних винятків?**
Рекомендується реалізовувати стандартні конструктори: порожній конструктор, конструктор з повідомленням (`string message`) та конструктор, що приймає повідомлення та внутрішній виняток (`string message, Exception innerException`)[cite: 20]. Крім того, додаються конструктори для ініціалізації власних властивостей[cite: 20].

**3. Поясніть патерн Result. У яких випадках його використання є більш доцільним, ніж викидання винятків?**
Патерн Result — це підхід, при якому метод повертає спеціальний об'єкт `Result<T>`, що містить успішний результат або інформацію про помилку (`IsSuccess`, `Error`, `Value`)[cite: 20]. Його використання доцільніше для очікуваних сценаріїв невдачі (наприклад, помилки валідації вхідних даних), оскільки це дозволяє уникнути використання винятків там, де помилка є частиною нормального потоку виконання[cite: 20].

**4. Які сценарії краще обробляти через винятки, а які через патерн Result?**
Через винятки слід обробляти виняткові, непередбачувані ситуації (наприклад, втрата з'єднання з базою даних, нестача пам'яті, пошкодження файлів)[cite: 20, 21]. Через патерн Result варто обробляти очікувані відхилення бізнес-логіки: невалідні вхідні дані, відсутність запису за ID у пошуку або недостатню кількість коштів на балансі[cite: 20, 21].
